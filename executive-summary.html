Deep dive · why H33-B2 (0.2778) and can we beat it?

H33-B2 is a pruning lineage, not a confirmed discovery gain

What the bytes establish. The frozen fleet audit identifies H33-B2 as a 40,199-dot prediction with 2,545 dots inside the mapped-fault halo removed, leaving 37,654 dots. GEMSDOE36's named historical file contains those dots plus 1,200 more. The h19-5 family (GEMSDOE24 → 25 → 27 → 28 → 30 → 31 → 32 → 33 → 36) adds zero new dots at every step: each step only removes dots within 1–2 px of catalogue faults.

Why it may have scored 0.2778 (mechanistic hypothesis, not identified causality). Under the distance-weighted Tversky metric (alpha=0.2, beta=0.8, R=300 m triangular kernel) the score is DTI = T / (0.2·T + 0.2·F + 0.8·G): false-positive mass F is weighted, so removing redundant dots near excluded known traces reduces FP cost while the triangular kernel can still credit dots that sit within 300 m of concealed truth. That is a plausible explanation for a scalar gain — but without hidden truth and the organizer's masking implementation, the hidden TP/FP/FN changes cannot be reconstructed from 0.2778. A different dot count or filename does not predict a higher score.

Can we generate a submission that scores higher than 0.2778? Not by repeating this lineage: the pruning ceiling is exhausted (every step removed dots; none recovered a concealed fault). Beating it requires recall of catalogue-absent faults — placing dots where unmapped fault geometry actually exists, outside the catalogue halo. Five not-yet-holdout-validated hypotheses are ranked in docs/hypotheses-beat-02778.md (step-over/relay-ramp connector completion; 3DEP scarp matched-filter; vent-feeder alignment along magnetic edges; K–Th–U radiometric alteration along lineaments; drainage-response traces). None has beaten the same-protocol holdout best with a paired 95% CI lower bound > 0, so none may consume a weekly submission slot yet.

Score-labeling rule. Every number in this project is labeled HOLDOUT-DTI (evaluator version, withheld positives, 95% CI), ORGANIZER-CONFIRMED (copied from a submission-page receipt), or explicitly a projection. A projection is never written as a score. 0.2778 is none of the above: it is an unverified owner report.

How to make a submission into the contest

Submission format and pre-flight check

  1. Get the template. Through an authorized DrivenData session, download sample_submission.tif from the competition data page and place it at data/raw/sample_submission.tif (do not auto-download; the page redirects to login and this project holds no credentials).

  2. Generate one single-band GeoTIFF. Float32, EPSG:32611, 3730×3292, 100 m north-up, transform identical to the template; finite values in [0, 1] inside the template footprint; NaN/nodata outside it. Mapped-fault pixels are masked by the organizer, so they carry no score.

  3. Validate locally before uploading.

    python scripts/validate_submission.py <file>.tif --template data/raw/sample_submission.tif --json <file>.validation.json
    Exit 0 = all published-format checks passed. Exit non-zero = do not upload.
    single band · float32 · EPSG:32611 · shape/transform match template · 100 m north-up grid · finite [0,1] inside footprint · null/NaN outside footprint · template readable. No NaN inside the footprint; values in [0,1]; CRS/shape/transform match the template.

  4. Name and note (≤140 characters). Give the submission a unique name (never a renamed historical file) and a note of at most 140 characters.

    Never reuse a historical file name or a renamed stopped raster.

    0 / 140 characters

    Example note: offcat corridor dots d3; unique vs GEMSDOE24/25/27/28/30/31/32/33/36 registry. The submission writer rejects notes longer than 140 characters, so this counter matches the gate.

  5. Upload on the DrivenData submission page. File to submit + note, then create submission. Up to three feedback submissions per week; one final selection is scored on both label sets (rules PDF).

Why your prior upload was rejected

The portal error "Predicted values must be in range [0, 1]" is explained by the two outside-footprint conventions in this repo:

  • -zeros rasters (e.g. GEMSDOE32 H33-B2, GEMSDOE36) write 0.0 outside the footprint. They pass a naive whole-array [0, 1] check but fail the published contract, which requires null/NaN outside the footprint.
  • -nan rasters write NaN outside the footprint (the published contract). They fail a naive whole-array [0, 1] check, because NaN is not in [0, 1] — exactly the rejection you saw.

DrivenData's private validator behavior is unverified here, so the safe artifact is the published-format one: finite [0, 1] inside the footprint, NaN outside, validated with the command above. This page offers no downloadable submission TIF while the stop is in force.

  3. Beat the current same-protocol holdout best with a paired 95% CI lower bound > 0; check surface and final dots against the complete current registry before placement and again on final dots; validate the exact saved bytes with the submission validator.
