Why the earlier “range” error happened, and why it cannot happen with this file

Two mechanisms were measured on this competition's own rasters on 2026-10-03; the earlier “cause undiagnosed” wording is withdrawn. (1) training_features.tif declares nodata as the float32 sentinel -3.4028234663852886e+38, and all 19 bands carry it on 3,061 pixels inside the 5,167,373-pixel scoring footprint (band 6 tc: 3,073; 58,171 band-pixels total). (2) Band 1 calls only 5,165,852 pixels valid against the template's 5,167,373, so a footprint mask taken from a feature band strands exactly 3,061 scored pixels as NaN. Either defect alone triggers the rejection.

scripts/build_portal_submission.py takes the footprint only from np.isfinite(sample_submission.tif), maps NaN→0.0 / ±Inf→1.0 / 0.0, clips to [0, 1], writes zero outside, then re-reads the bytes from disk and refuses to exit 0 unless every one of the 12,279,160 cells is finite and in range. Zero-outside is legal on two verified grounds: the organizer's own reference solution ↗ writes its example with no nodata tag and finite values everywhere, and the owner ledger shows …_0c9199f14e62 = 0.1294 alongside …_allfinite = 0.1294 — identical scores, so outside cells carry no weight. Full measurement record: range-error root cause.

Also verified this session: DrivenData staff confirmed that “Pixels corresponding to known USGS/INGENIOUS faults are masked / excluded from evaluation, so they do not count towards penalty terms” (forum 11516 ↗). Dots on catalogue pixels are therefore worthless. The shipped file has 0 of 44,090 on catalogue; the GEMSDOE30 OOF GBM research artifact wastes 2,517.

File contract

Before you upload

  • One GeoTIFF band; data type float32.
  • Projected CRS matches the provided grid: UTM zone 11N, EPSG:32611.
  • 100 m pixels and the exact template shape, bounds, and geotransform.
  • Inside the template footprint, every value must be finite and in [0, 1].
  • Outside the data bounds the published format asks for null/NaN. This project's default is instead 0.0 outside — a deliberate, documented trade: it cannot trip the portal's [0, 1] range check, the organizer's own reference solution writes its example the same way (no nodata tag, finite everywhere), and the owner ledger shows an identical score for the two encodings (0.1294 vs 0.1294). A NaN-outside twin with bit-identical in-footprint values is also published if you prefer the literal wording.
  • Use the organizer-provided sample template; never invent the footprint or infer the grid from a screenshot.

Grid and outside-value requirements come from the official competition problem description ↗. The local validator checks them against the available template but cannot guarantee portal acceptance.

Diagnose the reported range error

“Predicted values must be in range [0, 1]”

The reported error is not diagnosed. The exact uploaded file was not identified, and the organizer's validator is private. Do not infer that outside NaNs caused the error: the published specification explicitly calls for null/NaN outside the data bounds. The local default check verifies finite, in-range values inside the footprint and the published outside convention; it cannot reproduce the private portal validator.

  1. Run the published-format local check on the exact file you intend to examine. It reports whether any in-footprint value is NaN/Inf or outside [0, 1], and separately verifies the template grid and NaN-outside values.
  2. If the in-footprint value check fails, inspect the model output and data conversion that created that exact file. Do not silently clip or rescale; fix upstream and rebuild.
  3. The optional --finite-all-cells flag tests a stricter whole-raster diagnostic. NaN outside will fail that diagnostic by design; this says nothing about organizer behavior and is not the published file contract.
python scripts/validate_submission.py FILE.tif --template data/raw/sample_submission.tif
# Optional diagnostic only (not an acceptance test):
python scripts/validate_submission.py FILE.tif --template data/raw/sample_submission.tif --finite-all-cells

A single fold is only a screen: use all frozen folds and a fresh-seed confirmation. The seed-30 loss screen passed the first test and failed the second. The initial geometry weight is a test setting, not a selected optimum.

Competition limits worth remembering

  • The public leaderboard is not the private test set; a public increase can be overfit.
  • The official rules allow up to three weekly platform submissions and require one selected final submission for both prize rounds. Confirm current rules and deadline before any upload.
  • The public leaderboard changes over time. DrivenData Terms of Use prohibit automated monitoring/copying, so this page uses dated snapshots rather than a scraper.
  • The 2026 homepage and rules PDF show different deadline times (11:59 p.m. UTC versus 5:00 p.m. ET); confirm the controlling cutoff with the organizer.
  • Rules require a narrative disclosure of generative-AI use if applicable. Maintain a truthful method and tool-use record for the eventual submission package; the current-session disclosure draft must be updated and entrant-approved before use.
