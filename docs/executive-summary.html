2 · Why GEMSDOE32’s H33-B2 (0.2778) tops the nine sites

The mechanism: denominator hygiene, not new geology

PhD-level assessment. The h19-5 family score chain — h19-5 (0.1922) → D2.8 (0.2600) → r1 (0.2708) → H33-B2 (0.2778) → PINN (0.2750) — adds zero new dots at every step. Each step deletes dots progressively closer to catalogue faults:

  • D2.8 (0.2600): dots kept >2.8 px from catalogue faults.
  • r1 (0.2708): deletes exactly the 3,891 dots at 1.0 px from catalogue.
  • H33-B2 (0.2778): deletes exactly the 2,545 dots at 1.41–2.0 px from catalogue.
  • PINN (0.2750): adds 1,200 dots back, partially reversing the gain.

Because the organizer masks known-fault pixels pixel-exactly with no buffer, dots at 1–2 px from a catalogue trace are unmasked false positives, each paying the alpha=0.2 FP penalty in the distance-weighted Tversky metric. A dot at 3 px still earns kernel credit at 1–2 px (triangular kernel, R=300 m). The entire 0.2600→0.2778 gain is therefore FP-mass reduction, not recovery of any concealed fault.

Consequence: the pruning ceiling is exhausted. Beating 0.2778 requires recall of hidden faults, which carry beta=0.8 false-negative weight (4× the FP weight). Catalogue-recovery HOLDOUT-DTI and the public leaderboard measure different truths (withheld catalogue segments vs expert-mapped new faults). The h19-5 habitat is dense exactly where new geometry of existing systems lives — which a dispersed, off-catalogue emitter deliberately avoids.

Caveat: all four numbers above are owner-reported. No organizer receipt binds them to any file in any inspectable repository. The public leaderboard (live Oct 27: #1 = 0.4544) is not explained by any owner-reported figure; the gap cannot be closed by pruning alone.

4 · How to make a submission into the contest

Submission guide (download → validate → upload)

  1. Get the data. Through an authorized DrivenData session, download training_features.tif, labels.tif, and sample_submission.tif from the competition data page (login required; this repo cannot bypass access control). Place them in data/raw/.
  2. Prepare. Run python scripts/prepare_data.py to build the cached feature stack.
  3. Generate predictions. Use your model (or the vent-structural generator above as a template) to produce a 3730×3292 float32 probability grid on the sample_submission.tif grid.
  4. Write the TIF. Run python scripts/build_submission.py --probabilities <grid> --template data/raw/sample_submission.tif --name <slug> --note "<comment>". The note must be ≤140 characters (e.g. “clustering with k=25”). Use --outside nan (default) to match the published null/NaN-outside format.
  5. Validate locally. Run python scripts/validate_submission.py <output.tif> --template data/raw/sample_submission.tif. All 12 checks must pass: single band, float32, EPSG:32611, exact shape/transform match, finite [0,1] inside footprint, null/NaN outside.
  6. Check novelty. Run both stages: (a) rank-correlation with every registry raster ≤ 0.90 on the surface; (b) ≤70% of dots within 3 px of any registry raster’s dots. Log duplicates and stop — do not perturb a stopped raster.
  7. Holdout gate. Score on the spatially-blocked hide-and-recover holdout (alpha 0.2, beta 0.8, 300 m triangular kernel). The candidate must beat the control with paired 95% CI lower bound > 0 on two seeds.
  8. Upload. Submit the GeoTIFF (or zip containing it) on the DrivenData submission page. Fill the note field (e.g. “clustering with k=25”). One final selection is scored on both label sets; up to three feedback submissions per week.

Common failure: “Predicted values must be in range [0, 1]”

This happens when the raster has non-finite or out-of-range values inside the scoring footprint, or when a naive whole-array range check sees NaN outside the footprint. The public GEMS spec requires finite [0,1] inside the footprint and null/NaN outside. Use --outside nan and validate with the shared writer — never clip/sanitize in-footprint values silently.
