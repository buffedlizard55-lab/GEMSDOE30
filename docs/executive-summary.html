PhD-level answer: why H33-B2 reported 0.2778, and can we beat it?

H33-B2 is a lineage pruning, not a new discovery

The GEMSDOE24/25/27/28/30/31/32/33/36 leaders are one emission family: h19-5-style power-law budget dots placed just off catalogue faults, successively pruned. GEMSDOE25 and GEMSDOE30 report the same D2.8-derived file (0.2600); GEMSDOE28's r1 and GEMSDOE31's solo-d28 match at 0.2708; H33-B2 (0.2778) is that intermediate with roughly 2,545 dots within ≤2 px of mapped faults removed, leaving 37,654; GEMSDOE36's reference adds ~1,200 dots on top. The mechanism is purely "denominator hygiene": removing catalogue-proximal dots cuts the α=0.2 false-positive term without adding any true positives. The pruning ceiling is exhausted — every further step in this family removes dots, so it cannot add recall of concealed faults, which carry the β=0.8 false-negative weight (4× the FP weight).

Can we score higher than 0.2778? Only with a genuinely distinct lane that recovers unmapped faults at low false-positive mass. This session's generated file is exactly that lane by construction (lattice-uncovered structural dots), but it cannot be scored here: the holdout gate is blocked (organizer labels require DrivenData login), so no HOLDOUT-DTI or leaderboard estimate exists. The responsible action is to download it for inspection only, complete the holdout gate on an authorized machine, and let the separate selector decide on a slot. No slot has been selected.

How to make a submission to the contest

Submission instructions

  1. Get the data through an authorized session. The DrivenData data page (competition data tab) requires login and redirects unauthenticated visitors. Place training_features.tif, labels.tif, and sample_submission.tif in data/raw/, then run python scripts/prepare_data.py. This repository does not handle credentials or bypass access control.
  2. Build on the holdout, not the leaderboard. Use the shared cached feature stack and src/gemsdoe30/holdout.py (hide-and-recover: withhold whole fault segments with a buffer; derive catalogue features only from visible faults; mask visible faults pixel-exactly; pooled DTI, α=0.2, β=0.8, 300 m triangular kernel). Test each feature alone — AUC > 0.90 means leakage until proven otherwise.
  3. Write the GeoTIFF with the shared writer (src/gemsdoe30/submission.py): single-band float32 GeoTIFF, EPSG:32611, 3730×3292, 100 m north-up grid matching the template, values finite in [0,1] inside the footprint, NaN outside. The writer fails before writing if in-footprint values are out of range — this is what causes the portal error Predicted values must be in range [0, 1] when a file with values outside [0,1] (or NaN inside the footprint) is uploaded.
  4. Validate locally first: python scripts/validate_submission.py <file>.tif --template data/raw/sample_submission.tif — require: no NaN inside the footprint, values in [0,1], CRS/shape/transform match the template, null/NaN outside.
  5. Upload on the DrivenData submission page: choose the single .tif (or .zip containing one GeoTIFF), give it a unique name and a note (optional, ≤140 characters) to tell submissions apart (e.g. clustering with k=25).
  6. Respect the caps: up to three feedback submissions per week; one final selection scored on both label sets. Promotion to a real slot is a separate selector step — do not spend a slot on a candidate that has not beaten the holdout best with a paired 95% CI lower bound > 0.
